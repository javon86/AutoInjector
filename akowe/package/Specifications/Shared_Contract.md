# Bookforge consolidated implementation contract
Revision BF-IRB-1.0.0 | 12 October 2026

## 1. Baseline, scope and authority
This is a newly consolidated working baseline created under the user's instruction to finish the blueprint. It does not certify whether the unavailable historical master was v1.0 or v1.3. The current module specifications and machine-readable contracts supersede the active instructions in all six supplied rounds. History/source_archive.zip is historical evidence only. No historical approval signature is invented. Production approval of an implemented build remains a later step; it does not prevent implementing this baseline.

There are 11 independent domain modules A-K and 142 public operations. Independence means separately owned behavior, workspace and testable interfaces. It does not require 142 deployments or 11 services. A single application with module boundaries and a shared transaction kernel is permitted. Each original operation ID and name is retained. Supporting operations described here are kernel functions, not additional user-facing modules.

The product supports an author/editor working on a project, its universe, plans, prose, art, state, edits, assembled books and QC. A project has branches, feature selections, output profiles and three configurable AI slots. The interface is a desktop browser workspace usable on Windows, with responsive read/review access on mobile. Persistent project data, permissions, backups and provider settings are required. Framework, database and desktop wrapping are implementation choices. Cloud collaboration and simultaneous multi-user editing are optional; optimistic concurrency remains required even for one author.

Mandatory capabilities are all 142 operations, direct invocation without completing an entire other set, durable resume, logic-first work, selected-output export and review. A project need execute only operations selected by its feature manifest. Art, magic, mystery, foreshadowing, print covers and extra export formats are conditional project features. No application or provider is built by this handoff. No guarantee of narrative correctness or defect-free software is made.

## 2. Reading order and precedence
Read this file, the relevant per-set specification, its Contracts/SET/OP.schema.json and OP.operations.json, then its Acceptance_Cases/OP.cases.json. These documents are complementary: schemas define structural data; module text defines semantics. A structural PASS does not override a failed semantic rule. Any contradiction discovered during implementation is a defect to report against this revision, rather than permission to silently reinterpret behavior.

The schema bundle contains CREATE, UPDATE, READ, VALIDATE, ACCEPT, OUTPUT and RESPONSE definitions. Use #/$defs/ACTION for request validation. CREATE runs the domain operation and persists an immutable draft/result. UPDATE supplies a complete replacement of owned result data with exact base_ref; this intentionally replaces the old inconsistent patch/update aliases. A patch is a separate proposal that the owner converts to this replacement after checking its preconditions. READ retrieves the exact referenced record and writes no domain record. VALIDATE rechecks the referenced candidate. ACCEPT approves it when all owner rules and required approval evidence pass. REPORT, RUN and PROPOSE in historical prose map to CREATE; REWRITE and REBUILD map to CREATE a replacement candidate followed by owner acceptance. Historical wire modes are never accepted on the final API.

All modes require the scope OP:action, project access and branch access. principal_id is matched to the authenticated principal, not trusted from the body. Scopes come from the server's authorization store. Unknown project, record or operation is NOT_FOUND; inaccessible content is PERMISSION_DENIED without revealing its existence. Schemas/registry are loaded by the bootstrap kernel before I or K jobs run.

## 3. Canonical reference and values
Reference is exactly {project_id,branch_id,owner,module_id,record_id,version,content_hash}. All seven fields are required. owner must equal the first letter of module_id. version is an integer >=1. The target must exist in the same authorized project/branch, have the declared logical owner, version and SHA-256. Cross-branch reads require explicit branch permission and an explicit copy/merge proposal; a same-branch consumer rejects accidental foreign pins. Legacy id/revision, entity_id/version, artifact_ref strings and source_ref strings are not alternative forms.

For every *_ref or *_refs field, resolve and validate the canonical reference before domain work. Field names do not grant ownership. When a field names a specific producer (e.g. outline_ref), use the producer bindings in Contracts/interface_registry.json. Evidence/context collections can contain multiple permitted owners and retain each item separately. References to non-record input files are converted to imported, versioned records with owner I and provenance before use.

Hash input is UTF-8 JSON with keys recursively sorted, no insignificant whitespace, non-ASCII characters retained and no NaN/Infinity. Hash the immutable stored content including project, branch, owner, module, record ID, version, data and source pins, excluding the hash field itself. Do not Unicode-normalize stored text as part of hashing. Binary files use SHA-256 of exact bytes. Persist serialization bytes so another implementation need not reconstruct floating-point spellings. Zero is reserved for no-record state; no Reference uses version zero.

SemanticRecord is a defined narrative structure {summary,facts,links}, not an arbitrary object. Its summary is prose; facts are typed subject/predicate/value assertions with source pins and effective interval; links are canonical references. Facts can be FACT, BELIEF, PLAN or UNKNOWN. Only FACT is eligible for approved canonical truth; BELIEF and PLAN stay labeled when included in context. Values are scalar JSON or flat scalar lists. Nested domain objects use the explicit field schemas. Unsupported fields fail INVALID_INPUT. Absent optional field means not supplied; empty arrays mean known empty; null is accepted only where the schema explicitly permits it and means unknown/not applicable as specified by the owner. Never coerce missing, null, zero and false into one state.

Story time is signed integer ticks in the project's configured unit, default seconds relative to narrative epoch zero. This supports fictional calendars; display labels are author-defined. All facts/events in one project use the same unit. Effective intervals are half-open [from,to), with null bounds meaning unbounded. If both bounds exist, to must be greater than from. Narrative order is distinct from chronological story_time. Operational timestamps/deadlines are RFC3339 UTC. Monetary quotas use integer minor units and a project currency code; tokens, bytes, milliseconds, mm, pt and pixels are always explicitly distinguished.

Text spans use Unicode code-point offsets [start,end) into the exact referenced text, not UTF-16 units or byte offsets. Require start <= end <= text length, exact text_hash of that span and a stable span_id. Rewrites invalidate old offsets. Re-anchor by stable span ID and matching precondition text; ambiguous matches block with SPAN_CONFLICT.

## 4. Ownership and record lifecycle
A owns foundational universe/baseline facts. B owns plans. C owns canonical manuscript structure and accepted prose; F owns editing proposals and review evidence, and submits prose changes to C. D owns visual interpretations/assets. E owns accepted story events and temporal state. G owns assembly/export artifacts. H owns QC reports. I owns storage, schemas, registry, provenance, approval/lock records and completion projections. J owns reconciliation proposals and decision records. K owns projects, queue attempts, scheduling and resource reservations. I stores all domain revisions as custodian; it cannot invent the content owned by another module.

A durable record consists of record_id, project_id, branch_id, owner, module_id, version, contract_version, data, source_refs, lifecycle, created_at, principal_id, provenance_ref, approval_refs and content_hash. Record ID is stable; revisions are immutable and increase by one in a transaction. CREATE allocates a new ID with a nonexistence precondition and base_ref=null. UPDATE compares full base_ref; a stale version, hash or ownership mismatch writes nothing. Approved/locked data are never edited in place. A changed candidate starts DRAFT and requires renewed validation/approval; prior approval cannot be reused for new content.

Lifecycle is DRAFT -> VALIDATED -> APPROVED -> LOCKED. Validation failure retains a DRAFT candidate and findings. LOCKED can only become SUPERSEDED through an explicit protected-change authorization and a new validated revision. Rejection marks the candidate REJECTED without changing the approved head. Operational response statuses BLOCKED/PARTIAL describe missing dependencies or incomplete work and are not approvals. NOT_APPLICABLE has selection_rule_id and reason with the exact feature manifest pin. APPROVED requires structural checks, semantic disposition of every blocking finding, resolved mandatory links and valid approval scopes. UNKNOWN never counts as approved.

A conditional link is mandatory for approval when an explicit selected requirement reads that link's facts. Unused optional references do not block drafts. If the concept asserts an entity, jurisdiction, naming rule or capability governed by linked canon, approval requires a resolved pinned reference to that authority. No scheduler can require another whole set's completion. I12 projects commit evidence (operation, output pin, input pins, validation pin, approvals and commit receipt); it never takes a worker's success claim as evidence.

## 5. Transactions, failure and recovery
The storage kernel atomically commits record revision, previous-head comparison, provenance, audit, idempotency receipt and outbox event. Kernel envelope validation does not call/enqueue I04 recursively. Modules may keep durable attempt checkpoints, but only owner-authorized storage commits publish results. If domain storage or assets cannot be committed, return PARTIAL or BLOCKED and retain checkpoint IDs; never claim APPROVED.

Idempotency scope is (project_id,branch_id,target_operation,idempotency_key). Store a hash of action, base_ref, payload and input_refs; exclude request/correlation IDs and deadline. A duplicate identical logical request returns the same logical result/reference; a different hash under the same key returns IDEMPOTENCY_CONFLICT. Before retrying a timed-out write, query the receipt. Retries retain the logical key and use a new attempt_id. Event deliveries are at least once; consumers deduplicate event_id and receipt ID. Reusing event_id with different event content is EVENT_CONFLICT.

At most three attempts total. Retry delays before attempts 2 and 3 are 1 and 2 seconds plus uniform jitter [0,base_delay], capped at 4 seconds and the deadline. Retry only TIMEOUT, UPSTREAM_UNAVAILABLE and RATE_LIMITED; INTERNAL_ERROR needs classification and is nonretryable by default. Permission, invalid input, stale versions, missing prerequisites, unresolved approvals and hard dependency cycles wait for correction. Do not keep requesting paid generation after an ambiguous timeout: query provider_job_id first. A provider without status/deduplication support blocks an ambiguous retry for a user decision.

Errors have code, JSON Pointer path, message and retryable. Required codes: MISSING_INPUT, INVALID_INPUT, NOT_FOUND, VERSION_CONFLICT, HASH_MISMATCH, PERMISSION_DENIED, UNSUPPORTED_CONTRACT, UPSTREAM_UNAVAILABLE, CAPABILITY_UNAVAILABLE, TIMEOUT, RATE_LIMITED, INTERNAL_ERROR, IDEMPOTENCY_CONFLICT, EVENT_CONFLICT, APPROVAL_REQUIRED, EXPIRED_APPROVAL, LOCKED_FACT, SPAN_CONFLICT, PATCH_OVERLAP, DEPENDENCY_CYCLE, LEASE_EXPIRED, QUOTA_EXCEEDED, CONTEXT_TOO_LARGE, VALIDATOR_UNAVAILABLE, TOC_NONCONVERGENCE. Reject unsupported contract_version before dispatch. Error responses have result=null and no newly published refs; an existing durable partial checkpoint may be linked only with PARTIAL.

Cancellation stops dispatch and cooperatively requests provider cancellation. Preserve checkpoints and receipts. A returned cancelled/stale attempt cannot publish. Resume validates input pins, permissions, approvals and current queue generation before starting a new attempt. A changed source produces a new logical request; do not silently reuse an idempotency key for changed content.

## 6. Dependencies, selections and provider behavior
Feature manifest is immutable by revision and includes required operation IDs, required output IDs, branch, phase, selected features and selected release profiles. Membership of required_operations is the definitive scheduling predicate. B08 requires mystery=true; B09 foreshadowing=true; D requires artwork=true or an explicit requested asset; E08 magic=true; G10/G14 print-specific requirements apply only to selected print output. Directly requesting a disabled operation returns NOT_APPLICABLE with the exact predicate. A changed manifest invalidates only results whose predicate/input selection changed.

Dependency edge is {producer_ref,consumer_operation,consumer_record_id,paths,kind,stage}. kind is HARD, CONDITIONAL or REVISION_FEEDBACK. paths are JSON Pointers into stored data. A change invalidates a consumer if a changed path equals, is an ancestor of, or a descendant of a read path; a whole-record read uses the empty pointer and sees all changes. Traverse versioned descendants with a visited set. Invalidation marks stale, retains history and queues revalidation; it does not regenerate everything or mutate unrelated hashes. Hard CREATE graphs must be acyclic after the explicit staged bootstrap rules. Report exact SCC nodes/edges on an unexpected cycle and hold the affected jobs.

Exactly three AI slots are configured (AI-1, AI-2, AI-3); code and deterministic tools are separate resource kinds, not extra AI slots. Slots store adapter ID, capability set, context limit, health, concurrent-job limit, authorized project access and quota unit. Prefer CODE or TOOL whenever the operation's required result is deterministic. Among eligible AI slots choose lowest estimated cost, then active load, then slot ID. Missing capability never permits silent quality or privacy degradation. Slots may remain unconnected; affected creative work holds with CAPABILITY_UNAVAILABLE and supports manual input. No provider brand, API key or subscription is mandated.

Provider adapter implements submit, status, cancel, capabilities and usage; credentials are stored in the deployment's secret store, never the project export/log. A provider call occurs only under configured user authorization. Context must contain verbatim protected/required facts and output schema. Optional descriptions may be compressed with citations. If mandatory context exceeds the selected slot, split on scene/pass boundaries while preserving constraints; otherwise block CONTEXT_TOO_LARGE. Unknown usage units block quota reservation. A local provider may declare monetary cost zero but still reports token/concurrency limits.

## 7. Workspace, privacy and accessibility
Each set has its own labeled workspace and operation navigation. Show required/optional fields, linked source revisions, draft/approval state, validation paths, dependencies, attempt status and resume controls. Common states: EMPTY explains the minimum first input; LOADING shows attempt and Cancel; DRAFT previews output; BLOCKED lists exact missing field/provider/approval and links to the responsible module; FAILED retains evidence and offers permitted repair/retry; STALE explains changed pins; APPROVED shows its exact revision. Never show a numerical progress bar as approval evidence. Manual mode requires user initiation for a run; automatic mode follows configured scope and gates.

Inputs auto-save draft edits after 500 ms idle or on navigation; show saved/error state. Never discard unsaved edits on failed save. Long text and assets remain accessible on narrow screens; forms and lists support keyboard, associated labels, focus visibility and errors linked to fields. Do not encode states by color alone. Destructive archive/deletion actions require an explicit scope-aware confirmation in the product. No permanent content deletion is part of ordinary repair.

Projects default private. Enforce project/branch access on reads and writes, including asset URLs and backups. Imported content is treated as data, not instructions to change security or ownership rules. Display exactly which external slot receives a context package; exclude secrets and unrelated project records. Local/private storage and cloud hosting are allowed deployment choices, presented before installation/provider setup. No undisclosed upload or telemetry of manuscript content is permitted.

## 8. Acceptance, evidence and release
Run verify_contracts.py for schema meta-validation, concrete positive/negative instances, path existence, operation coverage and reference definitions. Its successful result is CONTRACT_ARTIFACT_VERIFIED, not working software. Acceptance_Cases contains FUTURE_RUNTIME_TEST descriptions for business behavior, persistence, crash injection, concurrency and provider integration. Implement and execute them against the application and save actual expected/observed results, artifact pins, command, tool version, date and reviewer disposition. Do not turn those plans into PASSED entries.

A release candidate freezes source revisions, feature/output manifest, export byte hashes, template/font versions and approval policy. H10 reports book READY only when every selected mandatory check matches those exact pins and is PASS, with every semantic uncertainty resolved by an authorized review. NOT_APPLICABLE requires rule evidence; missing checker is UNKNOWN. A new content/export revision invalidates affected evidence. Production application release separately requires build provenance, security/access checks, backup/restore rehearsal and release-owner approval; signatures authenticate actual approvals, never document author's guesses.

## 9. Stored binary artifacts, audit evidence and plan uncertainty
A Reference can address a JSON domain record or a binary artifact produced by the same owner operation. Storage knows its representation from immutable object metadata (kind=JSON_RECORD or BINARY_ARTIFACT), not from guessing the filename. A binary artifact metadata record has record_id, project_id, branch_id, owner, module_id, version, mime_type, byte_length, storage_uri, content_hash and source_refs. Its content_hash is exact file-byte SHA-256. A descriptor's artifact_ref/storage reference points to a distinct binary record ID; it never points recursively to its own descriptor. Retrieve JSON records with the producer OUTPUT validator; retrieve binary records with binary metadata validation plus byte-hash verification. D/G may commit both a binary record and a JSON descriptor in one logical receipt. Output routes in the interface registry accept these explicitly named representations; consumers needing a file must resolve the BINARY_ARTIFACT and verify its MIME/profile.

Similarly, C persists a prose record with candidate_events=[] first, then a separate C-owned event-candidate bundle referencing that immutable prose pin. Events are never self-referential to the content hash of the bundle that contains them. The single logical request receipt can list both output IDs; duplicate delivery replays both IDs. E accepts events only when their referenced prose record has been accepted. Event extraction failure preserves the prose candidate and holds state acceptance; it does not fabricate evidence.

READ/VALIDATE completion uses a durable audit receipt containing request/action, principal, exact input pins, outcome, checked schema/policy version and timestamp. It does not need a new domain commit merely to be considered complete. I12 projects an AUDITED_READ or AUDITED_VALIDATION evidence record for those actions; mutating actions require COMMITTED_OUTPUT evidence. A stored audit report is I-owned. Fixture-origin receipts are allowed in isolated tests but cannot satisfy application production approval. Approved/locked records and release candidates require evidence_origin=AUTHORITATIVE. Waivers bind exact finding/source/action hashes and expiry; schema, ownership, stale base, hash mismatch and protected-lock violations are nonwaivable.

J05 affected_downstream_count=null means unknown impact. Such an option has cost=null and is not automatically ranked before known feasible options. Route missing impact evidence to J06/J11; never treat uncertainty as zero. If every option is uncertain or infeasible, return BLOCKED with a decision request.

Dependency matrix predicates have exact meanings: ALWAYS=true; FIELD_PRESENT tests key existence, not truthiness; EQUAL compares typed JSON values; IN tests membership; AND/ANY combine child predicates; REQUIRED_OR_DIRECT_REQUEST checks the pinned feature manifest or an authorized user run; FEATURE_TRUE reads a boolean from that manifest; SELECTED_BASELINE_NONEMPTY tests selected resolved A/B baseline refs; ALL_SELECTED_INPUTS_RESOLVED_AND_VALIDATED checks source pin resolution, structural validity, owner semantic findings and required approval evidence. Unknown predicates/unknown selected feature states block. Per-field optional source collections are validated whenever supplied; they become final approval dependencies only when a selected requirement/approved assertion reads them.

E APPLY/REPLAY requests pin the input state in current_snapshot_ref. CREATE produces a replacement candidate; ACCEPT/UPDATE checks that exact snapshot is still the accepted head before publishing. This keeps the CREATE envelope base_ref=null while still rejecting state computed from a stale snapshot. Replay without a prior checkpoint starts from the approved baseline; checkpoint_ref is required only if a recorded checkpoint is selected.

## 10. Closure revision BF-CLOSURE-1.1
This section and the revised contracts apply to BF-CLOSURE-1.1 and replace conflicting statements in earlier sections of this current baseline. BF-IRB-1.0.0 remains the source baseline; its archive is unchanged. Wire contract_version remains BF-IRB-1.0.0 for this preimplementation consolidation; schema compatibility is not claimed for software built against the old bundle. Pin the entire final package manifest before implementation.

Canonical Reference owner must equal module_id[0] in schema validation as well as storage. Field bindings in interface_registry are normative; broad context/evidence collections permit any producer only as context, never substitute unrelated records for typed prerequisites. F owns findings/patches, so F output is never a manuscript. A visual style is D01; C12 text style cannot substitute for it. Consumer resolution first validates the producer record, then the field's selected data/representation, then authorization, lifecycle and exact hashes.

I01's AUXILIARY import mode stores an auxiliary_record={record_kind,data}; owner_operation=I01. Source and approval refs retain their existing null/draft policy. The auxiliary data must match Contracts/shared/AuxiliaryRecord.schema.json. Store the same auxiliary_record in I01 OUTPUT; canon_id identifies this imported record and revision equals its version. Kernel seeds/imports initial source/policy profiles before consumers run, using explicit user source and I authorization. This does not require prior G/H completion or add a domain module. Profile consumers require the declared required_record_kind; merely resolving some I01 record is insufficient. Different auxiliary kinds are incompatible even under the same producer ID. Record export includes the auxiliary data and source/approval pins.

G descriptors point to distinct binary IDs. G01-G09/G14 intermediate artifact bytes are UTF-8 JSON validated against the corresponding GxxArtifact schema in artifact_registry. G10's JSON layout descriptor refers to the actual staged cover file via layout_asset_ref. G11-G13 produce actual PDF/EPUB/DOCX bytes; format-specific parsers remain future application acceptance. sha256 equals artifact_ref.content_hash; revision equals binary version. validation_report_ref points to an I04 validation record for the staged binary/decoded structure, produced after binary allocation and before descriptor acceptance, so no descriptor self-hash is required. I04 validates subject_payload against its pinned schema and requires subject_ref.content_hash to match the staged subject; validation never fabricates a final approved export.

An immutable JSON record hashes identity, version, contract version, data and source_refs as the specified serialized bytes. Lifecycle, approval attachments, validation receipts and current-head pointers are separate versioned audit projections and are excluded from this content hash. ACCEPT/LOCK do not edit the content bytes. A changed data/source revision receives a new content hash and fresh acceptance evidence. I provenance/receipt IDs are allocated before the transaction; their edges cite the content pin and are not hashed into that same content. The transaction publishes all associated pointers atomically.

B11 target_length is exactly {value:positive_integer,unit:words|chapters}; absent is an owner-proposed size, never zero. Contracts/predicate_registry.json defines canonical plan/entity/thread predicates, values and extensions. A plan item uses its stable subject_id and must include plan.item_id matching that ID, unique plan.order within plan.parent_id, and plan.objective. Chapters/scenes additionally declare plan.event_ids, plan.pov_id, plan.location_id and plan.obligation_ids (known empty lists allowed; null POV/location stays undecided and blocks approval if the selected job needs it). B10 planned event subjects require the same stable event IDs and causal predecessor IDs; time uses Fact effective_from. Unknown/contradictory required objectives block final acceptance. Free prose summary does not establish these machine values. Extensions require a registered immutable schema/meaning/unit and owner; unsupported automatic predicates yield UNKNOWN and review.

E state is the SemanticRecord snapshot facts indexed by (entity subject_id,predicate,effective interval), not arbitrary fields of SemanticRecord. Event paths resolve through predicate_registry.event_paths; an extension event path requires an explicit registered mapping. An event addresses one entity; a multi-entity narrative action is an ordered batch with one typed event per entity committed atomically. before/after describe full old/new scalar or list. SET uses after; ADD/REMOVE require exactly one scalar list membership addition/removal and unchanged other items, uniqueness and exact before. Missing prior value is unknown null and cannot satisfy a known before. Apply in (story_time,scene_order,event_order,event_id) order; entity IDs and event IDs are unique. REPLAY needs current_snapshot_ref and superseded_event_ids, but checkpoint_ref is optional; absence replays approved baseline. INITIALIZE requires no current head. CHECK does not publish a new state head. Baseline sources and snapshots are validated for the same subject/unit/branch. Unauthorized event status claims cannot create accepted events; E verifies accepted prose, evidence span and owner disposition.

C02-C11 OUTPUT candidate_events is always [] for the first immutable prose record. Extracted candidate events are stored in a separate C-owned CEventBundle record; its prose_ref and every event.source_ref pin that first prose record. Its own hash has no self-reference. Bundle type is immutable metadata and uses CEventBundle schema instead of prose OUTPUT. E receives event values only after resolving the bundle and accepted prose/evidence; a bundle is not a chapter/manuscript input. C failure after prose commit keeps a DRAFT checkpoint and empty events, then retries extraction without repeating paid prose generation. This supersedes the ambiguous inline event instruction.

D01-D11 outputs have no map graph/sidecar properties. D12 requires both graph and sidecar; graph/sidecar are separately allocated D12 auxiliary records validated with MapGraph/MapSidecar schemas and metadata record_kind, not image descriptors. Initial geometry may be extracted deterministically from approved A04 coordinates, or imported as a D12 graph before render; no prior rendered map is required. D01 style JSON retains style_name/style_rules/publishing_format/palette in stored asset bytes, bound by exact file_hash. D09 JSON composition records canvas and placements from its inputs; D10 JSON check bytes retain findings/source pins. File resolution verifies kind and actual bytes before any consumer follows the URI.

K05 lease_state represents the queue's durable job projection: QUEUED, LEASED, WAITING, RETRYING, FAILED, CANCELLED or COMPLETED. Dispatch QUEUED->LEASED; owner gate/provider wait ->WAITING; transient classified failure ->RETRYING then QUEUED at next_attempt_at; unrecoverable ->FAILED; cancellation ->CANCELLED; authoritative receipt ->COMPLETED. Lease fencing/current generation rules still govern every publish. K07 next_attempt_at is RFC3339 only for RETRY and otherwise null; repair_request is null when no request exists. K09 expiry can be null for PENDING/REJECTED/REVOKED; APPROVED requires a future UTC expiry. K12 estimated_cost, quota.limit, usage.spent/reserved and remaining are integer currency minor units; quota.currency is explicit. Usage/limit comes from trusted storage, not caller-controlled balances. K11 resource currencies must match the reservation quota or the job blocks; this version does not perform exchange-rate conversion. K12 outputs remain projections of an atomic reservation ledger.

Release profile rules: H09 and its selected export operations are mandatory for every actual output; PRINT_WRAP_COVER additionally requires G10 and print interior page count. H05 checks selected chapter IDs; H08 applies when navigable headings/TOC are selected; H06 applies only to selected art. H02-H04 apply to selected canon/plot/arc obligations; their absence requires an explicit no-selected-obligations manifest reason. A supplied required_checks list cannot waive an applicable mandatory format integrity check. OUTPUT_PROFILE font_profile_ref is always pinned; page_profile_ref is null only for reflowable EPUB. Print profiles require nonnull printer_profile_ref. Page safe margins/bleed must leave positive usable width/height. Font embedding permissions and actual fonts remain approval gates.

For E/F/J fact/spans, semantic validation compares effective bounds, reference hashes, Unicode code point range and exact text substring hashes; these relational checks are not certified by isolated JSON Schema validation. Domain-reference fixture checks are compatibility tests on synthetic producer-owned records and exact hashes; they are distinct from application storage, provider execution and real publication approvals.

F12 approval_ref is optional during CREATE so a polish candidate can be generated and previewed before its exact output hash is known. C acceptance of the polish replacement requires the valid authorization for that exact candidate; prior source approval cannot authorize changed output. K12 denied reservations return allowed=false,reservation_id=null,remaining=max(0,limit-spent-reserved) and mutate no reservation; an allowed result requires the stored reservation ID.

For the first I01 AUXILIARY import, source_ref may be null because no record exists yet; import_evidence is required and binds source_label, source_sha256, authenticated principal_id and UTC imported_at. source_sha256 is SHA-256 of the exact imported source bytes, retained with the kernel import receipt. Require body principal to match the authenticated importer; validate auxiliary data before committing. Later revision imports pin their prior/source record. Non-AUXILIARY I01 writes still require a resolved source_ref. This explicit trusted import path creates first profiles without recursively requiring another imported record.
